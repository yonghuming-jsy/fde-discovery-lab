# 多租户知识库与 LLM Wiki MVP 技术方案

> 本方案依据两张白板整理。最新白板将产品范围明确为 FastAPI、Harness、知识库 RAG/LLM Wiki（知识图谱）和 SaaS 分层权限；之前出现的 examcoo.com 只按公开参考来源处理，不默认把在线考试系统作为本项目主体。

## 1. 产品目标

构建一个可本地 Docker 启动的多租户知识库 SaaS。租户管理员可建立组织层级、管理用户和知识库；用户将文档导入知识库，通过 RAG 检索获得带来源的回答，并从文档生成可浏览的 LLM Wiki 和知识图谱。

一期支持 Ollama 本地推理。回答须基于可访问的知识库内容并给出引用；证据不足时明确说明。模型生成的知识摘要和图谱需显示来源，不作为未经审核的事实自动覆盖原始文档。

## 2. 白板约束与范围

- 服务端：Python 3.11+、FastAPI。
- 部署：Docker Compose；PostgreSQL 持久化业务数据。
- 本地模型：Ollama；模型名称和服务地址由环境变量配置。
- AI Harness：本项目提供统一运行层，负责请求上下文、租户权限范围、检索、模型调用、输出校验、审计和基础评估。白板没有指定商业 Harness 产品或 Python 库，因此一期实现可替换的内部接口。
- 知识库：文档导入、分块、向量嵌入、RAG 问答、来源引用、LLM Wiki 和实体关系图。
- 权限：平台管理员（SaaS）、租户管理员、组织单元管理员、普通用户；组织单元支持父子层级。
- 旧白板出现的 examcoo.com 仅作参考或未来知识源候选；未经确认不抓取网站、不复制品牌或专有内容。

## 3. 用户与权限模型

### 角色

- **平台管理员**：创建、停用租户，创建首位租户管理员，查看 SaaS 级运行状态；默认不读取租户文档正文。
- **租户管理员**：管理本租户用户、组织树、知识库和租户配置。
- **组织单元管理员**：管理自己组织单元及子单元中的成员和知识库。
- **普通用户**：读取可访问知识库、查看已发布 Wiki 并进行问答；不能创建知识库、导入资料或生成/发布 Wiki。

### 层级与隔离规则

- 所有业务记录都带 tenant_id；数据库查询必须先限定当前租户。
- User 在每个租户有一个主组织单元和角色；组织单元采用 parent_id 树结构。
- 租户管理员可访问本租户全部组织单元。组织单元管理员可管理自身及后代单元。普通用户仅可访问所在单元及显式共享到租户的知识库。
- 知识库可绑定一个组织单元；unit_id 为空表示租户级共享。跨租户访问始终拒绝。
- 平台管理员身份不能绕开租户数据访问；任何临时支持访问都须显式授权并审计。

## 4. 核心流程

1. 平台管理员创建租户和首位租户管理员。
2. 租户管理员创建组织单元树并邀请或创建用户，分配租户角色和组织单元。
3. 管理员或获授权用户创建知识库，上传 UTF-8 文本或 Markdown 文件。
4. 系统将文档分块，通过 Ollama 生成向量并保存文档、分块和来源元数据。
5. 用户提问时，AI Harness 先检查知识库访问权限，再在该租户及该知识库内检索相关分块，将引用上下文交给 Ollama 生成回答。
6. 知识库管理员可触发 Wiki 更新：Harness 从授权文档中抽取实体、关系和摘要；结果标记生成时间与来源文档，管理员可审核。
7. 系统记录问答、检索引用、耗时、模型和输出校验结果，供租户管理员复核质量。

## 5. 技术架构

采用模块化单体，按职责划分 API、认证授权、知识库、检索、Wiki、模型适配和审计。

- **API**：FastAPI、Pydantic，统一前缀 /api/v1，自动提供 OpenAPI。
- **数据库**：PostgreSQL、SQLAlchemy 2.x、Alembic。业务表包含租户外键；小规模 MVP 将向量保存为 JSON 数组并在应用层做余弦相似度排序，规模扩大后可迁移 pgvector。
- **身份认证**：JWT Bearer token；Argon2 密码哈希；平台管理员由受控初始化命令创建。
- **Ollama**：HTTP 客户端适配器，分别配置聊天模型和嵌入模型，设置超时、错误处理和模型不可用降级提示。
- **AI Harness**：统一编排检索与生成。只向模型发送当前用户有权访问的上下文；保存引用；约束生成输出结构；记录审计与基础 RAG 评估指标。
- **前端**：响应式轻量 Web 控制台，包含登录、租户/组织管理、知识库、文档导入、问答和 Wiki 图谱查看。
- **容器**：Dockerfile、Docker Compose、健康检查、.env.example；Ollama 使用可选 profile，模型数据持久化，不默认下载大型模型。

建议代码层次：api、auth、permissions、knowledge、retrieval、wiki、harness、llm、models、schemas、db 和 audit。

## 6. 数据模型

- **User**：全局登录身份、邮箱、密码哈希、启停状态。
- **Tenant**：SaaS 租户和状态。
- **Membership**：用户在租户中的角色和主组织单元。
- **OrgUnit**：租户内的父子组织结构。
- **KnowledgeBase**：租户、可选组织单元、名称和访问策略。
- **Document**：知识库内的文档、原文件名、内容摘要、导入者和状态。
- **Chunk**：文档片段、顺序、来源定位信息和嵌入向量。
- **WikiEntity / WikiRelation**：图谱实体、关系、摘要和来源引用。
- **HarnessRun / AuditEvent**：模型、检索命中、引用、结果校验、耗时及管理操作。

## 7. API 草案

- POST /api/v1/auth/token、GET /api/v1/me
- POST /api/v1/tenants：平台管理员创建租户和首位租户管理员。
- GET/POST /api/v1/tenants/{tenant_id}/org-units
- GET/POST /api/v1/tenants/{tenant_id}/users
- GET/POST /api/v1/tenants/{tenant_id}/knowledge-bases
- POST /api/v1/tenants/{tenant_id}/knowledge-bases/{kb_id}/documents
- POST /api/v1/tenants/{tenant_id}/knowledge-bases/{kb_id}/ask
- POST /api/v1/tenants/{tenant_id}/knowledge-bases/{kb_id}/wiki/refresh
- GET /api/v1/tenants/{tenant_id}/knowledge-bases/{kb_id}/wiki
- GET /healthz

所有租户资源端点须在服务端校验身份、租户成员关系、角色、组织单元范围和知识库授权；不得只依赖 UI 隐藏按钮。

## 8. AI 输出、安全与质量

- 每个检索和模型调用均从已授权知识库开始，不接受客户端提交任意 tenant_id 来扩大访问范围。
- RAG 回答附带文档名和片段引用；无足够证据时拒答或说明资料不足。
- Wiki 实体、关系和摘要须携带来源文档/片段；用户可回看原文。
- 把输入文档和模型输出都视为不可信内容；提示词中明确禁止执行文档里的指令，输出需做结构、长度和引用校验。
- 限制导入文件类型、字节数、文档数、分块数和模型请求耗时。
- 不把真实租户文档发往外部模型；一期只接入本地 Ollama。
- 审计记录不得包含密码、访问令牌或整份敏感文档。
- Harness 记录 retrieval hit rate、引用覆盖率、无证据回答占比和耗时；这些指标只作质量信号，不替代人工判断。

## 9. 交付阶段

1. 基础服务、数据库迁移、平台管理员初始化、认证和租户隔离。
2. 组织层级、用户管理、角色校验和知识库 CRUD。
3. 文档导入、切块、Ollama 嵌入、RAG 检索和引用回答。
4. AI Harness 审计与校验、LLM Wiki 实体/关系生成和知识图谱展示。
5. Docker Compose、初始化说明、示例环境变量和操作文档。

## 10. 待确认事项

- “Harness”是否指特定产品/库；当前按可替换的 AI 运行与治理层理解。
- Wiki 图谱是否允许自动发布，还是必须经管理员审核后对租户可见；一期默认标记生成状态并由用户触发更新。
- 支持的输入格式、单文件大小、文档删除/重建策略，以及是否需要 PDF/Office 解析。
- 组织单元层级的成员继承和知识库共享规则是否需更细粒度控制。
- 生产环境是否部署独立向量数据库；MVP 暂用 PostgreSQL JSON 向量。
